# AI 待复核队列的服务端账本合同

日期：2026-10-05。此交付范围是队列归属、权限、迁移与原子确认服务端；识别上下文随后完成专项，见 [识别账本上下文](AI_RECOGNITION_LEDGER_2026-10-05.md)。Web/Android 生产入口仍待接入。正式服务及主应用未升级，不能将本专项视为整个 AI 账本合同完成。

## 数据与权限

- `AIReviewItem.Uid` 是账本所有者，`LedgerId` 是选定账本，`CreatorUid` 是提交人。共享数据写入所有者数据分片；个人默认账本 `0` 保留原语义。
- 直接账本成员可以读取本账本队列。所有者/管理员可处理全部队列，普通成员只处理自己的队列，只读成员不能写入。创建、状态变更、确认及回执重试均检查当前成员权限，写入事务内再次复核，不依赖家庭组。
- 原表通过启动时 schema 同步增列，再补 `CreatorUid = Uid`。旧行保留原来源、识别结果、状态和时间，继续属于默认账本；重复启动不迁到其他账本、不推断历史流水、不重建财务数据。旧无键记录使用 SQL NULL，允许同一用户保留多条历史记录。
- 创建回执绑定所有者、提交人、账本、稳定 `clientSessionId` 和内容 hash。非默认账本创建要求稳定键；重复同内容返回原队列 ID，内容改变返回 409，删除后的原键返回删除回执。
- 活跃队列纳入账本删除预览及事务中的引用保护；软删除不移除历史回执。

## 会话接口

所有接口属于正常登录会话。API Agent 令牌沿用失败关闭的路由规则，不能借其记账权限读取队列来源或调用新确认接口；MCP 队列接入尚未开放。

| 路径（`api/v1/ai/review/` 下） | 合同 |
| --- | --- |
| `capabilities.json` GET | 按 `ledgerId` 验证当前读权限，`Cache-Control: no-store`；合同版本 1、原子确认/持久创建/内容绑定/删除回执能力；能力声明不授予写权限 |
| `list.json` GET | `ledgerId`、`status`（1 待处理、2 已确认、3 已忽略）、`beforeId`、`limit`（1–100）；ID 倒序游标分页，客户端必须完整分页后才能清理缺失缓存 |
| `get.json` GET | `ledgerId` 与 `id` 精确读取；含删除回执、原流水 ID、提交人、确认人及可编辑权限 |
| `create.json` POST | 选定账本、稳定键、来源及识别草稿；创建不会改变余额 |
| `confirm.json` POST | `{ ledgerId, id, transaction }`；`transaction` 为用户明确确认后的完整收支/转账请求，含原稳定键；其账本必须与队列相同 |
| `dismiss.json` / `restore.json` POST | 待处理 → 已忽略、已忽略 → 待处理；不能将已确认记录恢复为待处理 |
| `delete.json` POST | 软删除且幂等，不删除确认回执 |
| `resolve.json` POST | 仅兼容旧默认账本无创建键记录的状态标记；共享及新有键队列返回 409，要求使用原子确认 |

ID 在 JSON 中均为十进制字符串。查询省略 `ledgerId` 保留默认账本兼容；新客户端必须显式保留来源账本，不随当前选择迁写。响应的 `editable` 是对象权限，实际操作还须结合状态判断。

## 原子确认与恢复

确认 hash 绑定完整编辑后请求及稳定键。事务按账本/成员、队列、账户及父账户、分类及父分类、标签和附件顺序锁定并复核实际归属、类型和可见状态；资源按 ID 排序锁定。队列状态、流水、转账双行、余额、标签索引、附件绑定及原流水回执在同一事务提交，任意失败全部回滚。

金额使用整数最小货币单位；退款冲减支出，同币种内部转账两边金额须一致，跨币种保留双金额。外部转入使用目标账户/目标金额，外部转出使用来源账户/来源金额；不存在的一侧账户及金额均为零，不使用另一侧金额作隐式替代。禁止用 AI 确认接口执行余额调整。共享非所有者不能使用所有者私有标签、附件，必须由客户端明确处理后再确认，服务端不静默移除。

流水所有者为账本所有者；`recorderUid`/`payerUid` 与 `ConfirmedUid` 保留实际确认人，原提交人不被覆盖。时间范围遵守确认人的现有编辑权限。

相同队列的相同冻结请求重复确认只返回原流水 ID；不同内容或不同键返回 409。即使原流水或队列之后被删除，相同请求也不会替代新增。权限撤销后连回执重试也拒绝，恢复权限后可重试原请求。旧 `resolve` 的已处理行没有原子回执，不能按来源、备注、时间或金额猜测对应流水。

旧客户端的“先新增流水、再 resolve”仍是两次请求，不能获得本接口的原子/幂等保证。后续客户端必须先持久保存账本、队列 ID、完整请求和键，再发送原子确认；未知结果锁定编辑并重试原快照，已知回执只读取原流水。不得在旧服务能力缺失时自动退回两次写入。
